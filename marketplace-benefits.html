A plugin packages a capability — skills, agents, hooks, MCP and LSP servers. A marketplace is the catalog that distributes those plugins. Together they turn ad-hoc, copy-pasted AI configuration into governed, versioned, organization-wide infrastructure.

00

Two concepts, one supply chain

The distinction matters because each solves a different organizational problem. A plugin answers “what capability?”; a marketplace answers “how does it reach every engineer, and who controls that?”

The catalog

Marketplace

“A plugin marketplace is a catalog that lets you distribute plugins to others.”[2] It provides centralized discovery, version tracking, automatic updates, and multiple source types.

Defined by a single .claude-plugin/marketplace.json that lists plugins by name and source.

The capability

Plugin

A self-contained directory of skills, agents, hooks, MCP servers or LSP servers, optionally alongside a .claude-plugin/plugin.json manifest.[1]

Its skills are namespaced — /plugin-name:skill — so two plugins never collide.

The relationship

A marketplace does not contain a plugin's code so much as point to it. One catalog references many plugins, and each plugin can be fetched from a different place — a folder in the same repo, another GitHub repo, a git subdirectory, or npm.[2]

Marketplace source

Where the catalog lives. Set when a user runs /plugin marketplace add. Supports a branch/tag ref.[2]

Plugin source

Where an individual plugin is fetched, set per entry inside marketplace.json. Supports both ref and an exact sha.[2]

02

Why this matters for an organization

Every benefit below maps to a concrete, documented capability — not a slogan. This is what changes when AI-engineering practice stops living in private dotfiles and becomes a shared, governed catalog.

01 / Consistency

One standard, everywhere

Coding conventions, review agents, and docstring rules ship as plugins “reusable across projects,” so every repo and every engineer inherits the same behavior instead of re-deriving it.[1]

use plugins to share with your team & community
02 / Onboarding

Set up in one command

A new hire runs marketplace add org/repo once. Install at --scope project and the toolset is committed to .claude/ and shared with the whole team.[4]

extraKnownMarketplaces auto-prompts on project trust
03 / Reproducibility

Versioned, deliberate updates

Pin a plugin to a version or a commit sha; users only update when you bump it. Run stable and latest as separate release channels.[2]

version → cache key → predictable rollouts
04 / Governance

Control what can be installed

strictKnownMarketplaces in managed settings locks the allowed sources — an empty array is full lockdown, an allowlist permits only approved catalogs. Users can't override it.[5]

security & compliance by policy, not trust
05 / Privacy

Keep it internal

Host the marketplace in a private repository; Claude Code uses your git credentials, and a GITHUB_TOKEN / GITLAB_TOKEN enables background auto-updates in CI.[2]

no public exposure of proprietary tooling
06 / Scale

Bake into images & CI

Pre-populate plugins at build time with CLAUDE_CODE_PLUGIN_SEED_DIR so containers start fully equipped — no runtime cloning, fully reproducible across the fleet.[2]

read-only seed, zero cold-start fetch
03

Plugin vs. standalone .claude/

Standalone .claude/ configuration is perfect for a single project or quick experiment. Packaging the same skills and hooks as a plugin is what makes them shareable, versioned, and governable — the official guidance recommends starting standalone, then converting to a plugin when you're ready to share.[1]

ConcernStandalone .claude/Plugin via marketplace @org
ReachAvailable in one project onlyShared across projects, teams, and the org
DistributionManually copied to shareInstalled with /plugin install from a catalog
UpdatesHand-managed, drift-proneVersioned; /plugin update or auto-update
NamingBare names like /deployNamespaced /plugin:deploy — no collisions
GovernancePer-machine, invisible to the orgAllowlisted & enabled via managed settings
Best forPersonal workflows, experimentsSharing, versioned releases, reuse at scale

How this repo is wired

# this repository IS the marketplace
omniagents/
├─ .claude-plugin/marketplace.json   # the catalog
└─ plugins/
   ├─ python/        .claude-plugin/plugin.json
   ├─ typescript/    .claude-plugin/plugin.json
   ├─ reviewer/      .claude-plugin/plugin.json
   ├─ code-review-graph/  …
   └─ … 10 plugins total

# each plugin entry just points at a folder
{ "name": "omniagents-python",
  "source": "./plugins/python" }

The catalog at .claude-plugin/marketplace.json lists ten plugins; each source is a relative path resolved against the marketplace root.[2] Because the marketplace is git-hosted, a plugin can omit version entirely and every commit becomes a new version — the simplest setup for actively-developed internal tooling.[2]

That single design choice is the whole value proposition: add the catalog once, and ten governed, versioned, namespaced capabilities arrive together.

Stand one up

  1. Create a pluginA directory + .claude-plugin/plugin.json + a skills/ folder. Test it with claude --plugin-dir ./my-plugin.[1]
  2. Write the catalogAdd .claude-plugin/marketplace.json with name, owner, and a plugins array of name + source.[2]
  3. Host itPush to GitHub (recommended), GitLab, or any git host — public or private.[2]
  4. Share itTeammates run /plugin marketplace add org/repo, then /plugin install name@marketplace.[4]
  5. Govern itUse extraKnownMarketplaces + strictKnownMarketplaces in managed settings to require and restrict sources org-wide.[5]
